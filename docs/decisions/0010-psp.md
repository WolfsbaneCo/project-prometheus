# 0010: PSP games

- **Status:** Accepted (first version implemented in `apps/prometheus64`; see "Not done").
- **Date:** 2026-11-12
- **Owner's choice:** PSP games in the same app and library as N64 and GBA games, the console recognised from the game file.

## How it works

| Part | Where | What it does |
|---|---|---|
| Recognising a PSP game | `src/psp_disc.cpp`, `src/library.cpp` | `.iso`, `.cso`, `.pbp` and `.chd` files are opened and checked: a UMD image must hold `PSP_GAME/PARAM.SFO` in its ISO 9660 file system (so another console's `.iso` is not listed), a `.cso` is the same read through its block index (raw deflate), a `.pbp` carries `PARAM.SFO` first. The game's ID (`DISC_ID`, like `ULUS10041`) and name (`TITLE`) come from there. Only a few kilobytes are read. A `.chd` is accepted by its header and named by its file. The id is `PSP-<disc ID>` |
| The core | `tools/build-psp-core-windows.sh` | PPSSPP (GPL-2.0 or later) at release v1.19.3, its libretro core, built into `cores/ppsspp_libretro.dll`. It draws with OpenGL through the same hardware-rendering path the N64 core uses (`RETRO_ENVIRONMENT_SET_HW_RENDER`, core profile) |
| Loading | `load_into` in `src/app.cpp` | The image is never read into memory or unpacked (they run to 1.8 GB): the core opens the file itself. PSP games are therefore not looked for inside `.zip`, `.7z` or `.rar` archives |
| PPSSPP's own files | `cores/PPSSPP` | The PSP's fonts (`flash0`), the list of per-game fixes (`compat.ini`), the pictures of the PSP's own dialogs (`ppge_atlas`), from PPSSPP's `assets`. The core looks for them in `<system folder>/PPSSPP`, so for a PSP game the system folder is the `cores` folder |
| Saves | `Memories\PSP` | The core's save folder is the PSP's memory stick: games save into `PSP\SAVEDATA\<game>` there, in the PSP's own layout, so a save folder copied from a real memory stick (or from PPSSPP) works as it is and can be copied back. Next to `Memories\N64` and `Memories\GBA` |
| Buttons | `Input::set_psp`, `src/input.cpp` | Cross = A, Square = B, Circle = C-Down (or C-Right), Triangle = C-Left (or C-Up), L and R, Start, Select = Z, the analog stick = the control stick, the D-pad = the D-pad. On a controller with the default bindings that puts Cross, Circle, Square and Triangle where a PlayStation pad has them (A, B, X, Y by position) |
| Picture | `apply_core_options`, `current_look` | Drawn by PPSSPP at a whole multiple of 480x272 that covers the screen's height (2x to 6x; **Resolution** in the menu sets it by hand, 1x to 8x) and shown as it is, 16:9. No N64 picture styles, textures or widescreen trick (the PSP is wide already) |
| Save states | as for the other consoles | F5 and F7, through the core's own serialisation |

## Building the core for Windows

PPSSPP's Windows builds are made with Visual Studio. This project builds its cores on Linux with MinGW-w64 (one pinned, reproducible build next to the other two cores), which PPSSPP's CMake files allow for but don't complete. `tools/build-psp-core-windows.sh` does what is missing:

- **FFmpeg.** PPSSPP plays the games' videos and some of their music with its own FFmpeg (the `ffmpeg` submodule). The copy it ships built for Windows links only with Visual Studio ("not compatible with mingw", its `CMakeLists.txt` says), so FFmpeg is built from that same source, statically, with the decoders PPSSPP's own Linux build script switches on. Without assembly (`--disable-yasm`), as PPSSPP's own Linux build does.
- **Header names.** The sources name Windows headers as Visual Studio users write them (`Windows.h`, `D3Dcommon.h`). On Windows any spelling opens the file; on Linux only the exact one. The script makes a folder of one-line headers that pass each such name on to the real one, and puts it on the include path. No source file is changed for this. The same is done for one library name (`Version`, which MinGW-w64 has as `libversion.a`).
- **Four socket options** (`TCP_KEEPALIVE`, `TCP_MAXSEG`, `TCP_KEEPCNT`, `TCP_KEEPINTVL`) that Visual Studio's headers name and MinGW-w64's don't: defined, with their Windows values, in the one-line header for `WS2tcpip.h`.
- **`GLEW_STATIC`** in the compiler flags: PPSSPP builds its own copy of GLEW (the OpenGL function loader) into the core, and on Windows GLEW's header assumes a separate DLL unless told so.
- **One change to PPSSPP's files:** its `CMakeLists.txt` runs a Windows batch file on every build (it stamps the version into the PPSSPP program's own resources). It can't run on Linux and the core doesn't use what it makes, so the script takes that line out, and stops if PPSSPP's text is no longer what it expects.

## Checked

- **Unit test** (`tests/psp_disc_tests.cpp`): an image built in the test (no game file) read as `.iso`, `.cso` and `.pbp`; another console's image, an empty file and a cut-off image refused.
- **In the app, on Linux** (PPSSPP's own test homebrew from its `pspautotests`, under Xvfb): the cube demo as `.iso` and `.pbp` listed in the library as PSP games, started, drawn at 3x filling the screen's height; the menu's PSP items; a save state saved and loaded; a resolution change (the core restarted and the game carried on); the controller test reporting Cross, Circle, Up, Start, L and the analog stick as pressed.
- **The Windows core:** built by the CI job "PSP emulator core (Windows)". On the development machine the cross-build was taken through every source file (the adjustments above are what it needed); the last steps, linking included, were left to CI.

## Not done

- **A real game on Windows.** Nothing here has been played by the owner yet; commercial games are the owner's to test (the app has none).
- **Google Drive backup of PSP saves.** They stay in `Memories\PSP` on the computer for now.
- **Online and ad hoc play.** PSP games play on one computer. PPSSPP's ad hoc networking is off.
- **PSP games inside archives.** Unpacking up to 1.8 GB each time a game starts isn't worth it; `.cso` is the compressed form to use.
- **File associations.** `.iso` belongs to many programs, so the installer leaves PSP files alone; drop them on the window or use the games folder.
- **Keyboard D-pad.** The arrow keys are the analog stick; the D-pad is T/F/G/H until rebound on the Controls screen.
